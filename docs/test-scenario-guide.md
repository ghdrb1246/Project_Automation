# 테스트 시나리오 사용 가이드

## 1. 역할

테스트 시나리오(testScenario) DB는 **"이렇게 동작해야 한다"는 기대 명세, 즉 테스트 케이스 자체**를 관리하는 곳입니다. 실제로 테스트했다가 실패한 것은 여기가 아니라 [QA 사용 가이드](./qa-guide.md)에서 다루는 별도 DB(QASheets)에 기록합니다.

```
테스트 시나리오 = 체크리스트 (무엇을 확인해야 하는가)
QA             = 체크리스트 돌리다가 걸린 것들 (실패한 것만)
```

## 2. 작성 시점

**기능 명세서가 완성된 직후, 개발 착수 전에 QA가 먼저 작성해두는 걸 추천합니다.** "무엇을 테스트할지"를 미리 정해두면 개발자도 어떤 케이스를 신경 써야 하는지 미리 알 수 있습니다.

## 3. 작성 방법

| 속성 | 작성 내용 | 예시 |
|---|---|---|
| 시나리오 ID | `SI-00N-P` 형식으로 순번 부여 | `SI-001-P` |
| 시나리오명 | 무엇을 테스트하는지 한 줄 | "비밀번호 불일치" |
| 카테고리 | 어떤 기능 영역인지 | "로그인" |
| 사전조건 | 테스트 시작 전 상태 | "유효한 아이디 존재, 비밀번호 불일치" |
| 테스트 절차 | 실제로 어떤 행동을 하는지 | "틀린 비밀번호 입력 후 로그인 클릭" |
| 기대결과 | 정상이라면 어떻게 동작해야 하는지 | "'비밀번호가 일치하지 않습니다' 토스트 노출" |
| 티켓 생성 | 비워둔 채로 시작 — 이 시나리오가 실패했을 때만 QA 페이지와 연결 | (비워둠) |

## 4. 시나리오를 잘 쪼개는 기준

하나의 기능에 시나리오를 여러 개 만들 때는 아래 관점으로 나누면 빠짐없이 커버할 수 있습니다.

- **정상 케이스**: 모든 입력이 올바를 때 (예: SI-005-P "로그인 버튼 활성화 조건")
- **입력 오류 케이스**: 잘못되거나 빠진 입력값 (예: SI-001-P "비밀번호 불일치", SI-004-P "로그인 버튼 비활성 조건")
- **존재하지 않는 대상**: 없는 계정, 없는 리소스 (예: SI-002-P "존재하지 않는 계정")
- **시스템/외부 오류**: 서버 장애, 네트워크 문제 (예: SI-003-P "서버 장애 발생")

기능 하나당 최소 이 4가지 관점을 한 번씩은 점검해보는 걸 추천합니다.

## 5. 실패했을 때

작성해둔 시나리오대로 테스트했는데 기대결과와 다르게 동작하면, [QA 사용 가이드](./qa-guide.md)를 참고해서 QA(QASheets) DB에 티켓을 생성하고 이 시나리오와 연결(Relation)하세요.

## 6. 자주 헷갈리는 부분 (FAQ)

**Q. ID 뒤에 붙는 `-P`는 무엇인가요?**
A. 현재 데이터 기준으로는 명확한 규칙이 확인되지 않았습니다(전부 `-P`로 통일되어 있음). 팀에서 화면 구분이나 우선순위 태그 용도로 의도하신 거라면, 그 의미를 이 문서에 추가로 정의해두는 걸 추천합니다.

**Q. 통과한 시나리오도 결과를 어딘가에 남겨야 하나요?**
A. 현재 구조에는 "최근 테스트 결과(통과/실패)"를 기록하는 속성이 따로 없습니다. 반복적으로 회귀 테스트를 돌리는 팀이라면, `최근 테스트 결과`나 `마지막 테스트 일시` 같은 속성을 이 DB에 추가하는 것도 고려해보세요.
