# 프로젝트 관리 자동화 테스트 체크리스트

구현가이드 최종본 기준으로 작성. 현재 GitHub에 브랜치만 생성하고 커밋은 하지 않은 상태를 전제로, **커밋(push)이 필요한 테스트**와 **지금 바로(수동 실행으로) 가능한 테스트**를 구분해뒀습니다.

---

## 0. 사전 확인

- [*] `NOTION_TOKEN`, `NOTION_WBS_DB_ID`, `NOTION_APISPEC_DB_ID`, `NOTION_FUNCSPEC_DB_ID`, `DISCORD_WEBHOOK_URL` — GitHub Secrets에 모두 등록되어 있고 값이 정확한지
- [*] Notion Integration이 WBS / API 명세서 / 기능 명세서 **세 DB 모두**에 연결(Connections)되어 있는지
- [*] WBS DB의 `Task ID` 속성이 `ID`(Unique ID) 타입으로 `WBS-1`~`WBS-12`가 채번되어 있는지
- [?] 브랜치명이 `feature/WBS-N-설명` 형식 규칙을 따르는지 확인 (지금 만드신 브랜치명도 이 규칙에 맞는지 한 번 점검)

> 지금 상태(브랜치만 생성, 커밋 없음)에서는 아래 **1번(Tier 1)**과 **"수동 실행" 표시된 항목들**부터 먼저 테스트할 수 있습니다. push 트리거가 붙은 항목은 최소 1개 커밋을 올려야 확인 가능합니다 (2-2, 4번 참고).

## 1. Tier 1 — Notion 자체 기능 (커밋 불필요, 지금 바로 테스트 가능)

### 1-1. 완성도 체크
- [*] API 명세서 페이지 하나를 열어 `URI`를 잠깐 지움 → `완성도 체크`가 `⚠️ 누락`으로 바뀌는지 확인
- [*] 다시 채워 넣음 → `완료`로 돌아오는지 확인
- [*] 기능 명세서 페이지에서도 동일하게 `기능 설명` / `시작 상태` / `종료 상태` / `API`(관계) 중 하나씩 비워서 확인

### 1-2. 동기화 필요 (Rollup + Formula)
- [*] 기능 명세서 페이지 하나 선택 → 연결된 API 명세서 페이지를 아무 내용이나 수정해서 저장
- [*] 기능 명세서의 Rollup `API 최종수정` 값이 갱신되는지 확인
- [*] `동기화 필요`가 `⚠️ API가 더 최근에 수정됨 — 확인 필요`로 바뀌는지 확인
- [*] 그다음 기능 명세서 페이지 자체를 저장(수정) → `동기화됨`으로 돌아오는지 확인
- [*] WBS 쪽도 동일한 방식으로 확인 (`연결 문서` → 기능 명세서 수정 → WBS의 `동기화 필요` 반응 확인)
- [*] `연결 문서`가 비어있는 WBS 항목(업무 영역이 미팅/개인 일정/백로그/Ops인 것)에서는 `⚠️` 없이 `-`로만 표시되는지 확인 — **이게 정상 동작입니다**

### 1-3. 신규 항목 추가 감지 (Database Automation)
- [*] API 명세서 DB에 테스트용 새 페이지를 하나 만들어봄 → 자동화가 발동해 담당자에게 알림이 오는지 확인
- [*] 기능 명세서 DB에서도 동일하게 확인
- [*] 테스트가 끝나면 만든 테스트 페이지는 삭제 (실제 데이터와 섞이지 않게)

## 2. Tier 2 — GitHub Actions

### 2-1. API 명세서 ↔ 실제 코드 비교 (`api-spec-check.yml`) — **커밋 필요**
- [] `src/routes/` (또는 실제 라우트 경로)에 테스트용 엔드포인트 하나를 추가하고 커밋 → push
- [] GitHub 저장소 `Actions` 탭에서 워크플로우가 자동으로 트리거되는지 확인
- [] 코드에는 있지만 API 명세서 DB에는 없는 상태이므로, API 명세서 DB에 "불일치" 코멘트가 자동으로 남는지 확인
- [] 반대 케이스도 확인: API 명세서에만 존재하고 코드에는 없는 엔드포인트를 하나 만들어서 같은 방식으로 테스트
- [] 정상 케이스(코드와 문서가 일치)일 때는 코멘트가 남지 않고 `일치함`으로 로그만 찍히는지 Actions 로그에서 확인

### 2-2. 불일치 플래그 알림 (`flag-notify.yml`) — **지금 바로 수동 실행 가능**
- [] GitHub `Actions` 탭 → `Notify Inconsistency Flags` 워크플로우 → `Run workflow`(수동 실행, `workflow_dispatch`)로 바로 실행
- [] Discord 채널에 메시지가 정상적으로 도착하는지 확인
- [] 현재 플래그된 항목이 없다면 `발견된 불일치 없음 ✅`이 뜨는지 확인 (이것도 정상 케이스)
- [] 1-1, 1-2에서 일부러 만들어둔 `⚠️` 상태가 남아있는 채로 실행해서, 해당 항목이 Discord 메시지에 정확히 나열되는지 확인
- [] (선택) Secret 값을 일부러 하나 틀리게 넣고 실행해서, 에러 로그가 원인을 파악하기 쉽게 나오는지 확인 후 다시 원상복구

## 3. Discord 알림

### 3-1. GitHub 앱 연동 (실시간 알림) — **커밋 필요**
- [] 위 2-1 테스트에서 만든 커밋을 push했을 때, Discord 채널에 커밋/PR 알림이 실시간으로 뜨는지 확인

### 3-2. 일일 현황 리포트 (`daily-discord-report.yml`) — **지금 바로 수동 실행 가능**
- [] `Run workflow`로 수동 실행
- [] 오늘~내일 마감인 WBS 항목이 정확히 표시되는지 확인
- [] 마감이 지난 항목은 `지연`, 아직 안 지난 항목은 `임박`으로 올바르게 구분되는지 확인
- [] `퍼블리싱 완료` / `배포 완료` / `최종 완료` 상태인 항목은 리포트에서 제외되는지 확인
- [] 담당자, 업무 영역이 실제 값과 일치하게 표시되는지 확인

## 5. (선택) AI 최소 검증 — **지금 바로 수동 실행 가능**
Tier 3까지 구현하셨다면:
- [] 기능 명세서와 API 명세서 내용을 의도적으로 모순되게 만들어서 `동기화 필요` 플래그를 발생시킴
- [] `ai-semantic-check.yml`을 `Run workflow`로 수동 실행
- [] Notion 코멘트로 "모순 가능성" 판정이 남는지 확인
- [] [Anthropic 콘솔](https://console.anthropic.com)에서 실제 호출 횟수와 토큰 사용량이 예상 범위(플래그된 항목 수만큼만) 내인지 확인
- [] 테스트 후 의도적으로 만든 모순 내용은 원상복구

## 6. 전체 시나리오 테스트 (End-to-End)

개별 기능이 다 확인됐다면, 실제 흐름 그대로 한 번에 테스트합니다.

- [] 새 기능 하나를 정하고, 기능 명세서 작성 → API 명세서 작성 → WBS에 태스크 생성 및 `연결 문서` 지정
- [] `feature/WBS-N-기능명` 브랜치 생성 → 실제 라우트 코드 구현 → 커밋 → PR 생성
- [] 각 단계마다 아래가 기대한 타이밍에 동작하는지 순서대로 확인:
  1. 커밋 push 시 Discord에 실시간 알림
  2. `api-spec-check.yml` 실행 → 코드-문서 일치 확인
  3. PR merge
  4. 다음날 `daily-discord-report.yml` / `flag-notify.yml` 실행 시 이 태스크가 정상적으로(또는 문제 있으면 플래그되어) 리포트에 반영
- [] 테스트로 만든 페이지/브랜치/PR은 정리 (실제 프로젝트 데이터와 혼동되지 않도록)

## 참고 — 지금 바로 시작 가능한 순서

커밋 없이도 확인 가능한 순서대로 나열하면:
1. **1번(Tier 1)** 전체 — Notion 안에서 값만 바꿔보면 됨
2. **2-2, 3-2, 5번** — `workflow_dispatch`로 수동 실행 (스케줄 기다릴 필요 없음)
3. 그다음 테스트용 커밋 1개를 만들어 push → **2-1, 3-1, 4번** 확인
4. 마지막에 **6번** End-to-End로 전체 흐름 재확인
