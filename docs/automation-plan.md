# 프로젝트 관리 자동화 기획서

## 1. 배경

이전 팀 프로젝트 회고에서 아래 네 가지 문제가 확인되었습니다.

1. 일정 관리가 제대로 되지 않아 마지막 날까지 몰림
2. 산출물(문서) 간 불일치가 많아 수정 작업이 반복됨
3. Notion에 데이터를 수동 입력해야 해서 팀원들이 사용하지 않음
4. 담당자 간 소통 부족으로 서로 무슨 작업 중인지 파악이 안 됨

이번 기획은 위 문제를 다음 프로젝트에서 반복하지 않기 위한 관리 체계와 자동화 범위를 정의합니다.

---

## 2. 설계 원칙

논의 과정에서 다음 세 가지 원칙을 확정했습니다.

| 원칙 | 내용 |
|---|---|
| **판단이 필요한 영역은 자동화하지 않는다** | 일정 수립은 PM의 판단이 들어가야 하는 영역이므로, 시스템이 대신 정하거나 코드 이벤트로 덮어쓰지 않는다 |
| **Notion을 단일 확인 창구로 삼는다** | 팀원이 여러 툴을 오가지 않고 Notion만 보면 현재 상태를 알 수 있게 한다. 다만 계산·판단 로직은 가능한 한 Notion 자체 기능(Formula, Rollup, Database Automation)으로 처리하고, 외부 스크립트는 Notion이 할 수 없는 것(코드 읽기 등)에만 사용한다 |
| **AI는 최후 수단으로, 최소로 사용한다** | 토큰 비용 문제로 AI 상시 연동은 배제한다. 규칙 기반으로 걸러지지 않는 애매한 케이스에 한해, 그것도 최소 컨텍스트·저비용 모델·배치 처리로만 사용한다 |

## 3. 문제 → 해결책 매핑

| 문제 | 해결 방식 | 자동화 여부 |
|---|---|---|
| 일정 관리 실패 | PM이 WBS(전체 일정표 + 팀원별 세부 일정)를 Notion에 직접 작성 | **수동** (의도적 결정) |
| 산출물 불일치 | 문서 간 연결 관계(Relation)를 이용한 불일치 자동 감지 + 담당자 알림 | **자동** |
| Notion 미사용 | WBS는 PM이 관리하므로 팀원이 별도로 입력할 항목이 최소화됨. 팀원은 GitHub 커밋/PR만 하면 관련 문서 상태가 자동 반영됨 | **자동(입력 부담 제거)** |
| 소통 부족 | Discord로 일정 임박/지연 현황 자동 리포트 + GitHub 이벤트 실시간 알림 | **자동** |

> 원래 GitHub 커밋 이벤트로 WBS의 상태·담당자를 자동 갱신하는 방안도 검토했으나, "일정은 PM이 직접 관리"하는 방향으로 결정하면서 WBS 자체에 대한 자동 쓰기(write)는 제외했습니다. 자동화는 **문서 불일치 감지와 알림**으로 범위를 좁혔습니다.

---

## 4. 자동화 범위 (Scope)

### 4-1. 자동화 대상
- 산출물(API 명세서 / 기능 명세서 / WBS) 간 **불일치 감지 및 담당자 알림**
- **신규 기능·엔드포인트 추가 감지** (코드에는 있는데 문서에 없거나, 문서에는 있는데 코드에 없는 경우)
- **팀 커뮤니케이션 자동화** (Discord 일일 현황 리포트, GitHub 이벤트 실시간 알림)
- **UML 다이어그램 자동 렌더링** (PlantUML, 코드 저장소와 함께 버전 관리되어 구조 변경 시 자동 반영)

### 4-2. 수동 유지 대상
- WBS(전체 일정표, 담당자별 세부 일정) 최초 작성 및 갱신 — **PM 담당**
- 산출물 최초 작성 — **각 담당자**
- 불일치 알림을 받은 뒤 실제로 무엇을 고칠지 판단하는 것 — **담당자 본인** (자동화는 "다르다"는 사실만 알려주고, 무엇이 맞는지는 사람이 판단)

## 5. 전체 구조 개요

실제 Notion 템플릿을 확인한 결과, 아래 관계가 이미 구성되어 있었습니다.

```
WBS(관련 항목) → 기능 명세서(API) → API 명세서
```

이 연결 관계를 그대로 활용해 3단계(Tier)로 불일치 감지를 설계했습니다.

| 단계 | 역할 | 처리 위치 | AI 사용 |
|---|---|---|---|
| Tier 1 | 필수 항목 누락, 문서 간 수정 시점 어긋남 감지 | Notion 자체 기능 (Formula/Rollup/Automation) | 없음 |
| Tier 2 | API 명세서 ↔ 실제 백엔드 코드 엔드포인트 비교 | GitHub Actions → 결과를 Notion 코멘트로 반영 | 없음 |
| Tier 3 | 문장 의미 수준의 불일치(규칙으로 못 잡는 것) | Tier 1에서 걸러진 후보만 AI로 재확인 | 최소 사용 |

Discord는 "확인 창구"가 아니라 "알림 채널"로만 사용합니다 — 최종 확인은 항상 Notion에서 하도록 해서 정보가 여러 곳에 흩어지지 않게 합니다.

---

## 6. 기대 효과

- 팀원은 평소처럼 코드 작업만 해도 문서 상태가 자동으로 점검됨 → Notion 수동 입력 부담 감소
- "누가 뭘 고쳐야 하는지"가 자동으로 지목되므로, 산출물 불일치를 마지막에 몰아서 발견하는 상황 방지
- 일정은 여전히 PM의 판단 아래 있으므로, 자동화로 인해 일정이 왜곡되거나 잘못 갱신될 위험이 없음
- AI 사용을 최소화해 비용 부담 없이 지속 운영 가능

## 7. 리스크 및 고려사항

| 항목 | 내용 |
|---|---|
| Notion 플랜 제약 | Database Automation의 알림 기능 일부는 유료 플랜에서만 제공됨. 팀 워크스페이스 플랜 확인 필요 |
| GitHub Actions 사용량 | 무료 한도 내에서 충분히 운영 가능한 규모이나, 트리거 조건(파일 경로 등)을 너무 넓게 잡지 않도록 주의 |
| AI 오탐 가능성 | Tier 3의 AI 판단은 참고용 알림이며, 최종 판단은 항상 담당자가 함 |
| 초기 세팅 비용 | Task ID 부여, Notion Formula/Rollup 구성 등 최초 1회 세팅 작업이 필요함 (구현 가이드 문서 참고) |

구체적인 설정 방법과 코드는 별도 문서 **`implementation-guide.md`**에 정리했습니다.
