# QA 사용 가이드

## 1. QA(QASheets) DB의 역할

QA는 **실제로 테스트해봤더니 기대와 다르게 동작한 버그 티켓**을 관리하는 곳입니다. "이렇게 동작해야 한다"는 기대 명세 자체는 [테스트 시나리오 사용 가이드](./test-scenario-guide.md)에서 다루는 별도 DB에서 관리하고, QA는 그 시나리오를 실행했다가 **실패한 것만** 기록하는 곳입니다.

**테스트를 통과한 시나리오는 QA에 아무 흔적도 남기지 않는 게 정상**이고, QA에 항목이 생겼다는 것 자체가 "뭔가 문제가 있다"는 뜻입니다.

## 2. QA 티켓 생성 방법

테스트 시나리오를 실행했는데 기대결과와 다르게 동작하면, QA(QASheets) DB에 새 페이지를 만듭니다.

| 속성 | 작성 내용 |
|---|---|
| 작업항목 | 실제로 관찰된 문제를 구체적으로 (예: "존재하지 않는 계정임에도 가이드 텍스트 미출력 이슈") — 시나리오명을 그대로 쓰지 말고 **무엇이 잘못됐는지**를 씁니다 |
| 시나리오 ID | 실패한 테스트 시나리오와 연결 (Relation) |
| 사전조건 / 테스트 절차 / 기대결과 | 연결된 시나리오에서 그대로 가져와 적음 (재현 방법을 QA 페이지만 봐도 알 수 있게) |
| DEV | 이 버그를 고칠 담당 개발자 지정 |
| QA | 이 버그를 발견/검증한 담당자 |
| 우선순위 | P0(당장 고쳐야 함)~P2 |
| 마감일 | 언제까지 수정되어야 하는지 |
| 진행현황 | 아래 3번 참고 |
| 버전 / OS 버전 / 디바이스 / 네트워크 | 재현 환경 정보 (특히 모바일 앱이면 중요) |
| 보고유형 | 버그 종류 분류용 (팀에서 아직 옵션을 안 정하셨다면 예: `기능 오류` / `UI 오류` / `성능` / `기타`로 정의해두는 걸 추천) |
| 출처 | 어떻게 발견됐는지 (예: `QA 정기 테스트`, `사용자 리포트`, `개발자 자체 발견`) |

## 3. 진행현황(상태) 값 — 추천안

현재는 대부분 `대기` 상태만 쓰이고 있어서, 앞으로의 흐름을 명확히 하려면 아래처럼 단계를 정해두는 걸 추천합니다.

```
대기 → 확인 중 → 수정 중 → 재검증 대기 → 완료
```

- **대기**: 티켓만 등록된 상태, 아직 아무도 안 봄
- **확인 중**: DEV가 원인 파악 중
- **수정 중**: 실제 코드 수정 진행 중
- **재검증 대기**: 수정 완료, QA가 다시 테스트해봐야 함
- **완료**: 재검증까지 통과, 종료

## 4. 자주 헷갈리는 부분 (FAQ)

**Q. 테스트를 통과하면 QA에도 기록을 남겨야 하나요?**
A. 아니요. 통과한 건 테스트 시나리오 DB에만 남아있으면 되고, QA DB는 실패한 것만 남기는 곳입니다.

**Q. 시나리오 없이 바로 버그를 발견했는데(테스트 케이스로 미리 안 써둔 경우)?**
A. QA 티켓은 먼저 만들고, 시나리오 ID는 비워두거나 나중에 관련 시나리오를 소급해서 하나 만들어 연결하세요. 다만 이런 경우가 자주 생긴다면 테스트 시나리오 작성이 부족하다는 신호이니, 다음 기능 개발 시 시나리오를 더 촘촘히 써보는 걸 권합니다.

**Q. WBS와 QA는 서로 연결해야 하나요?**
A. 지금 구조상 직접 연결되어 있지는 않습니다. 필요하다면 QA DB에 WBS 태스크로 연결하는 Relation을 추가로 만들 수 있지만, 지금 자동화 설계에는 포함되어 있지 않으니 필요성이 확인되면 추가하는 걸 추천합니다.
