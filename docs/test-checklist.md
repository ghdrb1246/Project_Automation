# 프로젝트 관리 자동화 테스트 체크리스트

구현가이드 최종본 기준으로 작성. 현재 GitHub에 브랜치만 생성하고 커밋은 하지 않은 상태를 전제로, **커밋(push)이 필요한 테스트**와 **지금 바로(수동 실행으로) 가능한 테스트**를 구분해뒀습니다.

---

## 0. 사전 확인

- [*] `NOTION_TOKEN`, `NOTION_WBS_DB_ID`, `NOTION_APISPEC_DB_ID`, `NOTION_FUNCSPEC_DB_ID`, `DISCORD_WEBHOOK_URL` — GitHub Secrets에 모두 등록되어 있고 값이 정확한지
- [*] Notion Integration이 WBS / API 명세서 / 기능 명세서 **세 DB 모두**에 연결(Connections)되어 있는지
- [*] WBS DB의 `Task ID` 속성이 `ID`(Unique ID) 타입으로 `WBS-1`~`WBS-12`가 채번되어 있는지
- [?] 브랜치명이 `feature/WBS-N-설명` 형식 규칙을 따르는지 확인

> 지금 상태(브랜치만 생성, 커밋 없음)에서는 아래 **1번(Tier 1)**과 **"수동 실행" 표시된 항목들**부터 먼저 테스트할 수 있습니다. push 트리거가 붙은 항목은 최소 1개 커밋을 올려야 확인 가능합니다 (2-2, 4번 참고).

## 1. Tier 1 — Notion 자체 기능 (커밋 불필요, 지금 바로 테스트 가능)

### 1-1. 완성도 체크
- [*] API 명세서 페이지 하나를 열어 `URI`를 잠깐 지움 → `완성도 체크`가 `⚠️ 누락`으로 바뀌는지 확인
- [*] 다시 채워 넣음 → `완료`로 돌아오는지 확인
- [*] 기능 명세서 페이지에서도 동일하게 `기능 설명` / `시작 상태` / `종료 상태` / `API`(관계) 중 하나씩 비워서 확인

### 1-2. 동기화 필요 (Rollup + Formula)
- [*] 기능 명세서 페이지 하나 선택 → 연결된 API 명세서 페이지를 아무 내용이나 수정해서 저장
- [*] 기능 명세서의 Rollup `API 최종수정` 값이 갱신되는지 확인
- [*] `동기화 필요`가 `⚠️ API가 더 최근에 수정됨 — 확인 필요`로 바뀌는지 확인
- [*] 그다음 기능 명세서 페이지 자체를 저장(수정) → `동기화됨`으로 돌아오는지 확인
- [*] WBS 쪽도 동일한 방식으로 확인 (`연결 문서` → 기능 명세서 수정 → WBS의 `동기화 필요` 반응 확인)
- [*] `연결 문서`가 비어있는 WBS 항목(업무 영역이 미팅/개인 일정/백로그/Ops인 것)에서는 `⚠️` 없이 `-`로만 표시되는지 확인 — **이게 정상 동작입니다**

### 1-3. 신규 항목 추가 감지 (Database Automation)
- [*] API 명세서 DB에 테스트용 새 페이지를 하나 만들어봄 → 자동화가 발동해 담당자에게 알림이 오는지 확인
- [*] 기능 명세서 DB에서도 동일하게 확인
- [*] 테스트가 끝나면 만든 테스트 페이지는 삭제 (실제 데이터와 섞이지 않게)

## 2. Tier 2 — GitHub Actions

### 2-1. API 명세서 ↔ 실제 코드 비교 (`api-spec-check.yml`) — **커밋 필요**
- [*] `src/routes/` (또는 실제 라우트 경로)에 테스트용 엔드포인트 하나를 추가하고 커밋 → push
- [*] GitHub 저장소 `Actions` 탭에서 워크플로우가 자동으로 트리거되는지 확인
- [*] 코드에는 있지만 API 명세서 DB에는 없는 상태이므로, API 명세서 DB에 "불일치" 코멘트가 자동으로 남는지 확인
- [*] 반대 케이스도 확인: API 명세서에만 존재하고 코드에는 없는 엔드포인트를 하나 만들어서 같은 방식으로 테스트
- [*] 정상 케이스(코드와 문서가 일치)일 때는 코멘트가 남지 않고 `일치함`으로 로그만 찍히는지 Actions 로그에서 확인

### 2-2. 불일치 플래그 알림 (`flag-notify.yml`) — **지금 바로 수동 실행 가능**
- [*] GitHub `Actions` 탭 → `Notify Inconsistency Flags` 워크플로우 → `Run workflow`(수동 실행, `workflow_dispatch`)로 바로 실행
- [*] Discord 채널에 메시지가 정상적으로 도착하는지 확인
- [*] 현재 플래그된 항목이 없다면 `발견된 불일치 없음 ✅`이 뜨는지 확인 (이것도 정상 케이스)
- [*] 1-1, 1-2에서 일부러 만들어둔 `⚠️` 상태가 남아있는 채로 실행해서, 해당 항목이 Discord 메시지에 정확히 나열되는지 확인
- [?] (선택) Secret 값을 일부러 하나 틀리게 넣고 실행해서, 에러 로그가 원인을 파악하기 쉽게 나오는지 확인 후 다시 원상복구

## 4. PlantUML 자동 렌더링 — **커밋 필요**
- [*] `docs/diagrams/` 아래 테스트용 `.puml` 파일 하나 추가(또는 기존 파일 수정) 후 커밋 → push
- [*] Actions 탭에서 `Render PlantUML` 워크플로우가 트리거되는지 확인
- [*] `.svg` 파일이 자동으로 커밋되는지 확인 — 아래 순서대로 확인
  1. Actions 탭에서 방금 실행된 `Render PlantUML` 워크플로우 실행(run) 클릭
  2. 로그에서 `Commit rendered diagrams` 단계를 펼쳐서, `git commit`이 "nothing to commit"이 아니라 실제로 커밋됐다는 로그(`M docs/diagrams/파일명.svg` 또는 커밋 해시)가 찍혔는지 확인
  3. GitHub 저장소 메인 화면 → **push했던 그 브랜치로 전환**(기본 브랜치가 아니라 방금 push한 브랜치, 예: `ci/ci-puml-init`) → `docs/diagrams/` 폴더로 이동
  4. 방금 추가/수정한 `.puml` 파일과 **같은 이름의 `.svg` 파일**(예: `architecture.puml` → `architecture.svg`)이 새로 생겼거나 갱신 시각이 방금으로 바뀌어 있는지 확인
  5. 저장소 상단의 커밋 히스토리(`Commits`)를 보면, `docs: auto-render UML diagrams`라는 커밋 메시지로 **워크플로우(`github-actions` 계정)가 자동으로 만든 커밋**이 하나 추가되어 있는지 확인 — 이게 사람이 직접 올린 게 아니라 자동화가 만든 커밋이라는 증거입니다
- [*] `.svg` 파일을 열어서(GitHub에서 파일 클릭하면 미리보기 렌더링됨) `.puml`에 작성한 다이어그램 내용과 실제로 일치하는지 확인
- [*] Notion에 해당 SVG의 Raw URL을 `/embed`로 넣어둔 페이지가 있다면, 최신 이미지로 갱신되어 보이는지 확인 — 아래 순서대로 확인
  1. **Raw URL 확인**: GitHub에서 방금 커밋된 `.svg` 파일을 열고, 우측 상단 `Raw` 버튼 클릭 → 그 페이지의 URL을 복사. 형식은 다음과 같습니다.
     ```
     https://raw.githubusercontent.com/{계정 또는 조직}/{저장소명}/{브랜치명}/docs/diagrams/파일명.svg
     ```
     지금처럼 아직 `ci/ci-puml-init` 같은 작업 브랜치에서 테스트 중이라면 URL의 `{브랜치명}` 자리에 **그 브랜치 이름**이 들어가야 합니다. 나중에 main으로 merge하면, main 기준 Raw URL로 다시 바꿔줘야 계속 최신 상태로 갱신됩니다(브랜치가 다르면 다른 URL이라 자동으로 안 바뀝니다).
  2. **Notion에 삽입**: 테스트할 Notion 페이지에서 `/embed` 입력 → 슬래시 명령 목록에서 `임베드`(Embed) 선택 → 위에서 복사한 Raw URL 붙여넣기 → 삽입
  3. **1차 확인**: 삽입 직후 다이어그램이 화면에 정상적으로 보이는지 확인 (링크가 깨져서 안 보이면 Raw URL 형식이나 브랜치명, 파일 경로 오타부터 재확인)
  4. **변경 후 갱신 확인 (핵심 테스트)**: `.puml` 파일 내용을 조금 바꿔서(예: 텍스트 라벨 하나 수정) 다시 커밋 → push → `Render PlantUML` 워크플로우가 자동으로 새 `.svg`를 커밋하는 것까지 확인
  5. **실제 판정 기준은 Notion 화면이 아니라 Raw URL 자체**입니다. 방금 복사한 Raw URL을 브라우저 새 탭에 직접 붙여넣어 열어서, 수정한 내용이 반영되어 있는지 확인하세요. 여기서 최신 내용이 보이면 → **파이프라인(렌더링→커밋)은 정상 작동하는 것으로 판정 완료**입니다.
  6. Notion 페이지 쪽 화면도 참고로 새로고침해서 확인은 하되, **Notion 임베드 화면에 옛날 이미지가 계속 보여도 자동화 실패가 아닙니다** — Notion이 외부 이미지를 자체 캐싱해서 생기는, Notion 쪽의 별개 표시 문제입니다. 브라우저 새로고침만으로는 이 캐시가 잘 안 풀리는 경우가 많습니다.
  7. **Notion 화면에서도 최신 이미지를 보고 싶다면**: 임베드 블록을 완전히 삭제하고 같은 URL로 새로 삽입하세요 (같은 URL을 그대로 재입력해도 Notion이 새 블록으로 인식하면서 캐시를 다시 가져오는 경우가 많습니다). 그래도 안 바뀌면, URL 끝에 임의의 쿼리 문자열을 붙여서(`...UCD.svg?v=2`처럼 매번 다른 값으로) 삽입하면 Notion이 이를 다른 리소스로 인식해 무조건 새로 불러옵니다 — 다만 이 방법은 값을 바꿀 때마다 Notion 쪽 URL도 다시 수정해줘야 해서, 팀 운영 단계에서는 "Notion 화면은 약간 지연될 수 있다"는 걸 그냥 감안하고 넘어가는 것도 현실적인 선택입니다.

## 6. 전체 시나리오 테스트 (End-to-End)
 
개별 기능이 다 확인됐다면, 실제 흐름 그대로 한 번에 테스트합니다. 아래는 **"북마크 추가"라는 새 기능**을 예시로 처음부터 끝까지 진행하는 구체적인 시나리오입니다. 실제 테스트하실 때는 아래 이름 그대로 쓰셔도 되고, 팀에서 안 쓰는 다른 기능명으로 바꿔서 진행하셔도 됩니다.
 
### 사용할 이름 정리
 
| 항목 | 값 |
|---|---|
| 기능명 | 북마크 추가 |
| API 메서드 / URI | `POST` / `/bookmarks` |
| API 명세서 페이지 제목(URI) | `/bookmarks` |
| API 이름(텍스트 속성) | 북마크 추가 |
| WBS Task ID | `WBS-13` (기존 WBS-1~12 다음 번호로 자동 채번됨) |
| WBS 업무 항목명 | 북마크 추가 API 구현 |
| WBS 업무 영역 | BE |
| 브랜치명 | `feature/WBS-13-bookmark` |
| PR 제목 | `[WBS-13] 북마크 추가 API 구현` |
| 라우트 코드 파일 | `src/routes/bookmarks.js` |
 
### 진행 순서
 
- [*] **① 기능 명세서 작성** — 기능 명세서 DB에 새 페이지 생성, 제목 `북마크 추가`. `기능 설명`, `도메인`, `시작 상태`, `종료 상태`는 **일부러 비워둔 채로** 다음 단계로 진행 (완성도 체크가 정상적으로 걸리는지 뒤에서 확인하기 위함)
- [*] **② 완성도 체크 동작 확인** — 저장 직후 `완성도 체크`가 `⚠️ 누락`으로 뜨는지 확인
- [*] **③ API 명세서 작성** — API 명세서 DB에 새 페이지 생성, 제목(URI) `/bookmarks`, `API 이름` = 북마크 추가, `메서드` = POST, `기능명` 관계를 ①에서 만든 기능 명세서 페이지와 연결
- [*] **④ 기능 명세서 보완** — ①로 돌아가서 비워뒀던 `기능 설명`(예: "사용자가 게시물을 북마크에 추가한다"), `도메인`, `시작 상태`, `종료 상태`, 그리고 `API` 관계를 ③의 페이지와 연결 → `완성도 체크`가 `완료`로 바뀌는지 확인
- [*] **⑤ WBS 태스크 생성** — WBS DB에 새 페이지 생성, 업무 항목명 `북마크 추가 API 구현`. 저장 시 `Task ID`에 `WBS-13`이 자동 채번되는지 확인. `업무 영역` = BE, `우선순위`·`마일스톤`·`작업일정` 채우고, `연결 문서`를 ①의 기능 명세서 페이지와 연결
- [*] **⑥ 코드 작업** — `feature/WBS-13-bookmark` 브랜치 생성 → `src/routes/bookmarks.js`에 `router.post("/bookmarks", handler)` 추가 → 커밋 → push
- [*] **⑦ 실시간 알림 확인** — push 직후 Discord 채널에 GitHub 커밋 알림이 뜨는지 확인
- [*] **⑧ 코드-문서 일치 확인** — `api-spec-check.yml`이 자동 실행되어, `/bookmarks` `POST`가 코드와 문서 양쪽에 다 있으므로 **불일치 없이 통과**하는지 확인 (Actions 로그에서 `code_routes`, `notion_routes` 양쪽에 `('POST', '/bookmarks')`가 찍히는지 확인)
- [*] **⑨ PR 생성 및 merge** — PR 제목 `[WBS-13] 북마크 추가 API 구현`로 생성 → `main`으로 merge
