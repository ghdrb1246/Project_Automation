# 요구사항 명세서 사용 가이드

## 구조

```
문제 정의 (한 문장)
└─ 도메인 (예: 인증)
    ├─ Entity 설명 (이 도메인에서 다루는 데이터 개체)
    └─ 기능(유스케이스) 단위로 반복:
        ├─ 시스템 처리: 시스템이 실제로 수행하는 동작들 (bullet)
        └─ 처리 결과
            ├─ 성공: 성공 시 어떻게 되는지
            └─ 실패: 실패 시 어떻게 되는지 + 실패 사유별 정리
```

이미 `인증(auth)` 도메인 아래 "토큰 발급" 기능이 예시로 잘 작성되어 있으니, **이 예시를 그대로 템플릿처럼 복사해서 다른 도메인/기능에 반복 적용**하시면 됩니다.

## 작성 예시

```
### 도메인: 북마크 (bookmark)
사용자가 관심 있는 게시물을 저장하고 다시 볼 수 있게 한다.

**Entity**
- Bookmark: 사용자와 게시물 간의 저장 관계를 나타내는 개체

**기능: 북마크 추가**

시스템 처리
- 사용자 ID와 게시물 ID로 북마크 레코드를 생성한다
- 이미 북마크한 게시물이면 중복 생성하지 않는다

처리 결과
- 성공: 북마크가 추가되고, 목록에 즉시 반영된다
- 실패:
  - 이미 북마크된 게시물 → "이미 북마크한 게시물입니다" 안내, 추가 안 됨
  - 존재하지 않는 게시물 ID → 북마크 생성 실패, 오류 반환
```

## 요구사항 명세서 ↔ 기능 명세서, 작성 순서

지금 두 문서가 다루는 레벨이 다릅니다.

| 문서 | 레벨 | 다루는 것 |
|---|---|---|
| 요구사항 명세서 | 상위(시스템 동작) | "이 기능이 왜 필요하고, 무엇을 해야 하는가" — 도메인/유스케이스 단위 |
| 기능 명세서 | 하위(API 스펙) | "그래서 어떤 API로 구현하는가" — 엔드포인트 단위 |

**작성 순서는 요구사항 명세서 → 기능 명세서 순**을 추천합니다. 요구사항 명세서에서 "북마크 추가"라는 기능과 성공/실패 케이스를 먼저 정의해두면, 기능 명세서에서 API를 설계할 때(`POST /bookmarks`) 이미 정의된 성공/실패 케이스를 그대로 응답 스펙으로 옮기기만 하면 되어서 훨씬 수월합니다. 순서를 건너뛰고 기능 명세서부터 쓰면, 나중에 "이 API가 왜 필요했는지" 맥락이 빠진 채로 코드만 남는 경우가 많습니다.
